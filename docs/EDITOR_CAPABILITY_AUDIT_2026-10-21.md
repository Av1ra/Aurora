# Aurora Editor: аудит возможностей игры и недостающих инструментов

Уточнение владельца: текущая задача ограничена транспортом. Продолжение — [углублённый транспортный аудит](EDITOR_TRANSPORT_DEEP_AUDIT_2026-10-21.md) и [подробный список критериев](EDITOR_TRANSPORT_CHECKLIST_2026-10-21.md). Разделы о зданиях/картах ниже сохраняются как справка и не включены в текущую реализацию.

Дата: 21 октября 2026. Проверенный код Aurora: `91de3ca` (установленная функциональная сборка `f4737f8`, версия 0.2). Установленный Steam build ID: `23935965`. Цель этого прохода — исследование и план; поведение установленного редактора не изменялось.

## Вывод

Aurora уже решает базовую задачу OBJ → NMF: материалы, несколько вариантов окраски, отдельные LOD, pivot, обычный груз, основные огни, дым, общие характеристики и превью. До полноценного редактора транспорта остаются существенные пробелы в форматах моделей, составных объектах и специальных параметрах техники. Некоторые существующие поля требуют исправления раньше добавления новых возможностей.

Сначала следует обеспечить корректное открытие и сохранение штатных машин. Затем добавлять сочленения, анимации и специальные инструменты по классам. Здания, карты и сценарии — отдельные направления интерфейса и форматов; их нельзя поместить в одну форму настроек автомобиля.

## Охват и ограничения

- Прочитаны 2 373 INI из 22 выбранных категорий базовой игры и установленных каталогов DLC/ELC. В транспортных категориях обнаружены 1 073 файла `script.ini`.
- Найдены 682 уникальных имени команд INI. Это словарь встреченных данных, а не число функций движка или процент поддержки редактором.
- Просканированы материалы и заголовки DDS в тех же категориях; игровые изображения и модели в репозиторий не копировались.
- Реальным классом `NativeModel` проверены все 4 063 NMF в 13 перечисленных ниже категориях. Это проверка открытия геометрии, не проверка игрового поведения, анимаций или качества изображения.
- Изучены документация по транспорту/зданиям/скинам, разъяснение разработчика по звукам и публикации разработчика о Building Editor и Early Start. Поиск в интернете ограничен доступными релевантными источниками; закрытые сообщества, весь Workshop и внутренний код движка не проверены.
- Не запускались окна игры, Model Viewer или редактора. Точное соответствие их поведения и нашего рендера остаётся ручной проверкой владельца. Сохранения и Workshop пользователя исключены из обхода.
- Категория каталога не всегда равна классу техники: в `dlc3/vehicles` лежат также поезда, суда и самолёты. Класс нужно определять по содержимому скрипта.

Данные: [команды и примеры](audit-data/game-capabilities.json), [таблица команд](audit-data/game-directives.csv), [совместимость NMF](audit-data/nmf-compatibility.json), [воспроизведённые ошибки скриптов](audit-data/compatibility-checks.json).

## Подтверждённые проблемы совместимости — исправлять первыми

### 1. Часть штатных основных моделей не открывается

| Каталог | Открылись / проверены |
| --- | ---: |
| vehicles, включая соответствующие DLC/ELC | 2 242 / 2 347 |
| trains | 280 / 285 |
| ships | 35 / 35 |
| airplanes | 82 / 98 |
| helicopters | 63 / 66 |
| cabins | 33 / 33 |
| buildings | 909 / 948 |
| resources | 100 / 100 |
| containers | 5 / 5 |
| trees | 38 / 44 |
| fences | 10 / 10 |
| paths | 27 / 27 |
| buildingeditor | 65 / 65 |
| **Всего** | **3 889 / 4 063** |

174 отказа нельзя считать 174 повреждёнными игровыми файлами: часть содержит форматы/потоки, которые наш парсер не поддерживает. Есть и реальные основные модели: `vehicles/bus_zis_155/main.nmf`, `vehicles/covered_rnt_agk/main.nmf`, `vehicles/covered_t138/main.nmf`, `trains/russian_loco_t3m2my/main.nmf`.

Причины различаются: animated/external nodes, потоки `4011a`/`13a`, дополнительные данные, неподдержанные заголовки. Нужно создать набор штатных примеров по каждой причине, расширять чтение и отдельно проверять обратную запись. Простое удаление проверок формата неприемлемо: успешное открытие не гарантирует безопасное сохранение.

### 2. Терминатор `$END`

В 26 INI транспортных категорий встречен `$END` (24 в vehicles, 2 в trains). Воспроизведено на `dlc3/vehicles/bbo214/script.ini`: `VehicleScript.Fields` воспринимает его как обычное поле, а `VehicleScript.Set` добавляет новое поле после него. В игре нужно проверить последствия, но сериализатор уже нарушает положение терминатора. `VehicleLights.Transform` также не считает `END` известной секцией.

Нужны общий разбор `end`/`$END`, сохранение исходного стиля и тесты, запрещающие активные новые поля за терминатором. Источник: `VehicleScript.cs`, `VehicleLights.cs`, `compatibility-checks.json`.

### 3. Составные параметры навыков скрываются

`trains/russian_service_agmu/script.ini` содержит `$SKILL_CONSTRUCTION_RAIL_CRANE 19 25`. Форма `Skills()` принимает только одно число через `double.TryParse`, поэтому этот параметр не отображает. Исходная строка сохраняется, но редактировать её нельзя.

Нужны типизированные поля с несколькими аргументами и подходящими названиями для каждого класса. Не следует превращать строку `19 25` в одно число или создавать универсальное поле без объяснимой схемы.

### 4. «Расход топлива» основан на устаревшей команде

`MOVEMENT_CONSPUMPTION` встречается в установленных данных, однако руководство по транспорту помещает её в раздел Obsolete. Поэтому нынешнее название в форме создаёт необоснованное ожидание управления расходом. Нужны актуальное подтверждение механики и контрольный эксперимент; до этого поле следует скрыть из обычного режима или явно обозначить как устаревшее. Параметр `LIFESPAN` существует, но его единицы и применимость также нельзя выводить только из имени.

Источник устаревшего статуса: [документация транспорта, раздел Obsolete](https://steamcommunity.com/sharedfiles/filedetails/?id=1861143159). Это исправляет прежнее предположение, что присутствия ключа в штатном INI достаточно для полноценной настройки.

### 5. Native-материал отображается не полностью

`MaterialDocuments.Native` забирает три текстурных слота. Native `DIFFUSECOLOR`, `SPECULARCOLOR`, `AMBIENTCOLOR`, `SPECULARPOWER` не превращаются в соответствующие настройки/значения нашего viewport; экспорт исходного текста и точное отображение — разные уровни поддержки. Нужны корректный импорт этих свойств, редактирование и отдельный режим сравнения с native-материалом.

`TEXTURE_NOMIP` найдена в 84 MTL; текущие регулярные выражения импортёра/экспортёра её не обрабатывают. Поэтому обещание собрать любые внешние текстуры пока слишком широко: проверка переносимости должна учитывать все типы ссылок. Это особенно существенно для будущего режима зданий.

### 6. DDS поддерживаются частично

В обследованных данных найдены DXT1 — 6 634, DXT5 — 8 107, DXT3 — 29, DX10/BC7 (`98`) — 18, DX10/BC6H (`95`) — 4 и другие/несжатые форматы. `DdsImage.Decode` поддерживает RGBA8, BC1, BC3 и часть BC5, но не все обнаруженные варианты. Часть текстур не откроется даже при правильных путях. Выходной Encode пишет RGBA8 без полноценной цепочки mipmaps.

Сначала нужны подтверждённые примеры BC2/BC7 и сохранение/генерация mipmaps. BC6H/HDR следует рассматривать отдельно для окружения, не обещать как обязательную функцию автомобильного материала.

### 7. Прочитанная страна и ограничения доступности

Встречается `COUNTRY_STR`, например Austria у `dlc3/vehicles/bbo214`. Форма начинает с числового `COUNTRY`, а ApplyPurchase удаляет `COUNTRY_STR`. Нужны явная поддержка строковой страны и сохранение исходного значения при неизменённой форме. Для составных моделей также нужны `FAMILY` и `PURCHASE_EXCLUDE`; календарь доступности не должен навязываться каждому вспомогательному объекту.

### 8. Значение «Стоимости» не подтверждено

Руководство описывает `COST_RUB`/`COST_USD` как выбор валюты с автоматически вычисляемой ценой, зависящей от характеристик. Форма же предлагает ввод денежной суммы и записывает её аргументом команды. Нельзя обещать, что введённые 4 300 означают цену 4 300 в игре. Требуются отдельная проверка текущей версии и корректное название поля; точную формулу без исследования не предлагать. Источник: [раздел Common документации транспорта](https://steamcommunity.com/sharedfiles/filedetails/?id=1861143159).

### 9. Несколько разрешённых грузов и бессрочная доступность

Форма выбирает только первую строку `RESOURCE_ALLOW_ONLY`; при изменении остальные исходные строки не показываются и остаются в документе. В установленном наборе найдено 6 таких скриптов. Нужен редактируемый список ресурсов и понятный режим «любой подходящий».

В 51 скрипте конечный год превышает 2100, например `$AVAILABLE 1971 3000` у `trains/russian_crane`. Нынешний валидатор не принимает этот год и скрывает следующие настройки. Нужен отдельный режим «бессрочно» при сохранении пользовательского диапазона ручного выбора 1900–2100. Результаты и примеры сохранены в [script-semantics.json](audit-data/script-semantics.json).

### 10. Вид привода не должен скрываться в названии эффекта

Документация связывает эффект `train_electric` с электрической тягой, включая троллейбусы. Поэтому универсальный выбор «дыма» недостаточен: требуется отдельное понятное представление привода/токосъёма и проверка совместимых эффектов по классу. Актуальность этой зависимости нужно проверить на штатных примерах текущей версии; произвольный новый ключ топлива придумывать нельзя.

## Инструменты качества и удобства

| Инструмент | Состояние / необходимое улучшение |
| --- | --- |
| Проверка перед сохранением | Есть отдельные запреты экспорта; нужен единый список проблем с выбором объекта: материалы, текстуры, LOD, части, анимации, имена, отсутствующие ссылки |
| Дерево сцены | Сейчас плоский выбор объекта; нужны hide/solo, несколько выбранных деталей и группа операций |
| Проверка размеров | Нужны габариты в единицах игры, измерение между точками и контроль масштаба OBJ перед конвертацией |
| Материалы | Нужны native/PBR-сравнение при одинаковом освещении, явные scalar/alpha-настройки, просмотр UV и карты отдельно |
| Нормали | OBJ уже умеет нормали/группы сглаживания; нужен диагностический просмотр и отдельная безопасная команда исправления, а не повторный импорт вслепую |
| Восстановление | Есть ручной `.aur` и история; нужны автосохранение, восстановление после аварии и журнал команд |
| Экспорт | Есть staging и сохранение исходников; нужен полный граф зависимостей и проверка результата после переноса в пустую папку |
| Совместимость проекта | Есть версия контейнера; нужны явные миграции схем и понятная реакция на проект с неизвестными инструментами/частями |
| Производительность | Для больших сцен полезны отмена долгой загрузки, асинхронная обработка и ограниченный кэш текстур; измерения ещё не выполнены, это предложения, не подтверждённые узкие места |

## Остальная игра: отдельные направления редактора

| Направление | Какие данные/инструменты понадобятся | Отношение к нынешнему редактору |
| --- | --- | --- |
| Здания | Тип/подтип, рабочие и посетители, производство/потребление, склады, стоимость и этапы стройки | Новая предметная модель и отдельный режим |
| Подключения | Дороги/пешеходы/рельсы/конвейеры, электрика, тепло, вода/канализация и станции транспорта | Визуальные точки/линии, направления, ограничения и профили здания |
| Подземные и дополнительные меши | Подземные модели, внутренние части, этапы строительства | Граф частей и связей со скриптом |
| Инфраструктура | Порты, аэропорты, депо, стоянки, места погрузки и позиции транспорта | Отдельные схемы с визуальной проверкой |
| Окружение | Деревья, ограды, ресурсы, контейнеры, декали/материалы | Профили ресурсов; возможность открыть геометрию ещё не означает готовый мод |
| Карты и ландшафт | Рельеф, водоёмы, биомы/погода, месторождения, границы, размещение | Полноценный редактор карт, отдельный большой проект |
| Сценарии, исследования, кампании | Цели, условия, события, этапы, локализация | Редактор логики и проверка ссылок; не настройки NMF |

Руководство по зданиям и описание встроенного Building Editor подтверждают самостоятельность этого направления: [документация зданий](https://steamcommunity.com/sharedfiles/filedetails/?id=1885817861), [публикация разработчика](https://www.sovietrepublic.net/post/report-for-the-community-2). Описанные здесь режимы Aurora пока не реализованы; способность парсера прочитать часть NMF не равна поддержке здания/карты.

## Основа дальнейшей реализации

1. **Архитектура:** схема команд по типу сущности и классу техники. Для команды хранить тип/число аргументов, привязку к объекту, источник доказательства, ограничения и статус active/deprecated/unknown. Один разборщик должен обслуживать форму, импорт, экспорт и преобразование координат.
2. **Безопасность данных:** сохранять неизвестные секции, оригиналы и внешние файлы. Перед преобразованием проверять все пространственные зависимости, а перед сохранением — весь пакет. Неподдержанный формат объяснять, а не молча упрощать.
3. **Масштабирование:** сцена как дерево объектов и связей: основная модель, LOD, суставы, внешние части, анимации, материалы, ресурсы. Не добавлять отдельную цепочку условий для каждой машины.
4. **Отказоустойчивость:** операции через существующий механизм команд/undo; импорт и сохранение должны фиксироваться целиком. Добавить автосохранение и восстановление. Повторная загрузка экспортированного комплекта должна быть проверкой результата.

Проект будущего визуального UI-плагина остаётся отложенным. WinUI, версия 0.2, одна общая поставка и ручные проверки владельца сохраняются.

## Порядок работ небольшими пакетами

| Пакет | Содержание | Критерий готовности |
| --- | --- | --- |
| A | `$END`, составные skills, строковые страны — последовательными циклами | Нативные примеры открываются в форме, меняются и сохраняются без потери соседних данных; новые поля перед терминатором |
| B | Дополнительные жёсткие NMF-потоки и данные | Подтверждённые проблемные основные модели открываются и повторно читаются после сохранения; анимации не теряются молча |
| C | Native scalar-материалы, неподдержанные текстуры и пути | Внешние зависимости собраны; исправлены конкретные DDS/MTL-примеры, есть визуальное сравнение |
| D | Проверка экспорта и дерево объектов | Из списка проблем можно выбрать объект; зависимость не пропадает при переносе комплекта |
| E | Колёса и сочленения | Штатный сочленённый автобус и обычный грузовик можно проверить в сцене; сборка экспортируется целиком |
| F | Перевозка техники и специальные механизмы | Грузовая площадка, пробная перевозимая модель и минимум один штатный механизм с корректной привязкой |
| G | Поезда, самолёты, вертолёты, суда — отдельными циклами | Для каждого класса есть собственные поля, визуальные точки и набор штатных проверок |

В каждом пакете сохранять ритм 2–3 связанных исправлений. Не начинать одновременно здания/карты/анимационный авторинг только ради увеличения количества пунктов меню.

Отдельный короткий цикл перед расширением форм: убрать недоказанные обещания «Стоимость»/«Расход топлива» и согласовать смысл этих настроек с действующей механикой. Здесь изменение поведения ещё не выполнено.

```powershell
python Packaging/audit-game-capabilities.py "<game>/media_soviet" docs/audit-data

```

Числа привязаны к установленному набору данных этого прохода. При добавлении DLC или обновлении игры результаты нужно пересоздать. Старые комментарии/документы проекта, расходящиеся с текущим исходником, не использовались как подтверждение отсутствия функции.
